# Game capacity lock: operational limits

All backend instances must run this version and use the same MongoDB database. Older instances, scripts and direct Mongo writes bypass this lock. This is a single global lock, not a lease: there is no expiry or automatic takeover. Acquisition uses a token and durable acknowledged writes. A process crash, uncertain database result, or unexpected server error may leave `game_capacity_locks/_id: global` present and block all guarded writes. Contenders fail with 503 after five seconds. Long photo uploads or other work inside a booking also hold the lock; throughput and availability are deliberately sacrificed for safety.

Recovery is manual and requires an operator: stop **all** backend instances and other potential writers, verify every former holder and in-flight operation has actually terminated and MongoDB is healthy, then inspect the stored lock token, capacity, and affected schedules and reconcile any uncertain or partial bookings. Only after ensuring no prior writer can resume, delete the lock by matching both `_id: global` and the observed token, then restart all instances on the same version. Never delete a lock merely because it is old, and never enable a TTL. A failed lock-release acknowledgment may leave an unknown outcome; follow the same investigation before retrying any booking.

Capacity reduction rejects a value below peak existing active/future occupancy, treating unknown legacy activity conservatively. Legacy schedule reconciliation and an initial capacity must be planned before rollout. Existing pre-lock deployments cannot be mixed safely. This mechanism does not provide transaction rollback for multi-schedule bookings or other side effects.
